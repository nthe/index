CodeCon 26 · Research note 02

A cheaper read can use more tokens.

Shunt sends broad code-reading work to a second model, then returns a short, cited answer to the main assistant. We examined Spotify’s published Shunt, the independent CC Shunt package, and related local Shunt experiments. A lower estimated bill can come with more tokens and more time.

01 / Mechanism

Move the reading, not the decision.

The parent assistant still owns the task. Shunt changes who reads the source. A hook can block a recognized broad read and direct the parent to Scout. Scout searches related files and returns a short answer with file and line evidence. The parent checks the evidence and continues.

  1. Ask a taskThe parent gets the user's question and decides what source evidence it needs.
  2. Route a broad readBy default, CC Shunt's local hook blocks some reads above 120 selected lines and tells the parent to call Scout.
  3. Scout searchesA worker model follows starting paths, finds related code, and checks relevant files.
  4. Return evidenceScout sends a concise answer with exact file and line references.
  5. Parent verifiesThe parent uses the answer, reads a short section if needed, then edits or tests.
Spotify and CC Shunt use different routes. Spotify Shunt sends work through Spotify Portal. CC Shunt's hooks and routing run in the harness; its tested Codex worker still used a provider-hosted model. “Offline” in the local research means “without Portal,” not “models run on the laptop.” [1] [4]
02 / Published claim

What Spotify measured

Spotify reports fewer tokens in Claude's context for three selected bulk-read comparisons in a 162,000-line Java repository. The published figures are not full-session cost or quality measurements. [1] [2]

Reported reduction: 82–94%, with a 90% mean. This compares direct source reads with short Shunt answers in the parent context. It does not count the worker's tokens as a full-session total.

The benchmark does not establish total cost, time, or answer accuracy. Its code estimates token counts from text size; it is not a matched, paid, end-to-end session audit. [3]

Scope matters: fewer tokens in one context is not the same measure as fewer tokens or lower cost across all models.

04 / Repeated results

CC Shunt saved 23.9%. A related variant saved 31.8%.

The CC Shunt README reports the 23.9% result for Scout MCP + hook v2. A separate Offline Shunt checklist run had the largest repeated saving in the local study: 31.8%. These results come from different cohorts and variants.

CC Shunt · 12 paired blocks · corrected broad-read hook

−23.9% estimated credits

Scout MCP + hook v2 cost less in 12 of 12 pairs. Median paired saving: 21.5%. The 95% bootstrap interval was 12.8% to 36.4%. All 12 answers passed review.

Offline Shunt · separate checklist cohort

−31.8% estimated credits

Estimated credits fell from 70.5007 to 48.0540. It cost less in 12 of 12 pairs. Median paired saving: 31.7%; 95% bootstrap interval: 26.9% to 37.7%. All 12 answers passed manual review and source checks. It used two Scout calls per block.

Do not merge these claims. They use separate cohorts and direct controls. The 31.8% result is from the related Offline Shunt checklist experiment, not evidence that the CC Shunt package produces that saving. This is not a randomized head-to-head test.
05 / Method and trade-offs

How to read the numbers

These figures come from one repeated upload-retry investigation in one code repository. The task traced a duplicate-upload billing issue through client retries, uploads, processing, and deduplication.

Paired task

Each 12-block cohort compared direct reading with its own delegated variant on the same upload-retry task and source revision. The parent model was gpt-6.1-sol at high effort; Scout used gpt-6-luna at high effort.

Cost estimate

Estimated Standard Codex credits used a rate card saved on 2 November 2026. Credits are not an invoice or a USD amount. Different model rates can lower cost even when token totals rise.

Token total

Counts include the parent and Scout. CC Shunt used 129.4% more tokens than direct reading. The separate checklist run used 181.1% more. Neither result is token compression.

Time total

Time sums parent CLI session durations, including time while the parent waited for Scout. It rose 184.5% for CC Shunt and 210.2% for the checklist variant. It is not wall-clock duration or a measure of parallel completion.

Answer review

Reviewers checked answers against the task's answer key and source evidence. All 12 answers passed in each 12-pair cohort. This was not an independent, blinded evaluation across many tasks.

Checklist timeout change

In the separate checklist run, three attempts timed out and were excluded. Blocks 7–12 were rerun with longer limits. All 12 included pairs had complete accounting and no Scout timeout. This is a protocol change to note.

06 / Limits

What this does not prove

Use the numbers for this task and setup. Do not treat them as a forecast for another team, model, or repository.

Not a Spotify comparison

We did not run Spotify Portal on matching prompts, models, source revisions, and rates. CC Shunt is an independent adaptation. It is not an official Spotify product or affiliated with Spotify.

One task and repository

The strongest repeated results cover one upload-retry investigation. Small trials on document search, translation, and one-file coding had mixed outcomes.

One harness and rate card

The live cost experiments used Codex. Checks for other harness adapters do not establish equal cost, speed, or behavior across those harnesses.

Routing is not a security boundary

The CC Shunt hook detects some broad reads. Some commands and pipes can pass through. The hook does not guarantee delegation or complete source coverage. The parent must check important evidence.

Cost can change with pricing

Credits are rate-card estimates. Model rates, cache use, and worker calls affect the result. A different rate card can change the size or direction of savings.

Time has a narrow meaning

Summed parent-session time rose. Runs could be parallel, so this is not elapsed wall time. The study does not show a faster user experience.

Practical rule: Use Scout when the task needs broad source discovery across many files and a cited summary can replace repeated reads. Read a short, known section directly when you need one fact. In either case, verify the evidence before you change code.
